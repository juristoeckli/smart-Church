# ChurchTools one-time migration

The Sync settings page can create a read-only preview and import a bounded snapshot from a configured ChurchTools installation. This is a one-time import into Smart-Church; it does not write to ChurchTools or establish ongoing synchronization.

## Supported mapping

| ChurchTools source | Smart-Church destination | Mapping and behavior |
| --- | --- | --- |
| Person | Contact | Stable ChurchTools person ID is kept in the migration crosswalk. First name, last name, email, and phone are mapped to standard fields; all non-credential fields returned by the configured persons endpoint are retained as a private read-only profile, including nested and custom fields. Relationships from `GET /persons/relationships` are retained with source person IDs and relationship type metadata. When both people resolve through the crosswalk, the People directory exposes their linked relationship to users with private People access. Unresolved relationships remain in the private profile. A matching email is reported for review and is never used by itself to merge people. |
| Group | Group | Stable group ID, name, and description are mapped. Memberships are connected when the person has a migration crosswalk or an existing ChurchTools source ID. Role, normalized status, and entry date are mapped when recognized in the member response. The importer adds memberships and keeps existing local membership details. |
| Event | Service or event | Stable event ID, title, date, start/end time, all-day state, location, room, description, volunteer positions, and time-plan items are mapped where the source provides them. Plan item title/name/label (including nested song title/name), start time, duration, and description/note are normalized. Position holders link only when their person ID resolves locally. |
| Song and arrangement | Worship song catalog | Smart-Church can store song titles, authors, keys, arrangement names, and HTTPS links to licensed charts/audio. ChurchTools agenda song titles may be retained as plan item titles, but no separate song/arrangement catalog record, source-ID link, author/key, licensed chart/audio reference, or per-item responsible-role link is imported. The migration preview lists unsupported agenda and nested-song field names without copying their values. |
| Resource | Bookable resource | Stable resource ID, name, supported category, description, location, capacity, approval requirement, and active state are mapped. Category values are normalized to Smart-Church's room, vehicle, equipment, or other values. |
| Resource booking | Booking / resource schedule | Not imported yet. The instance schema provides `GET /bookings` for occurrences overlapping inclusive local-date bounds and `GET /bookings/{bookingId}` for a stored series and its calculated occurrences. A recurring series can appear multiple times in the occurrence list, so import must deduplicate by stable booking ID. The model includes resource/person IDs, title, subtitle, description, date/time or all-day state, quantity, approval status and actor/time, recurrence, extra dates, excluded dates, and an optional linked calendar appointment. The requested history window still needs an owner decision. |

The importer preserves all non-credential fields returned by the configured persons endpoint in a private read-only profile; credential-like keys are recursively excluded. Person relationships are fetched separately and retained as profile metadata. The People API resolves imported relationships through the stable crosswalk and only returns them to users with private People access. Custom group-membership fields, planned group exit dates, membership remarks or waiting-list positions/history, event series/recurrence, event plans beyond the normalized fields above, song/arrangement records or their licensed links, per-item responsible-role links, position response states, and resource bookings are not imported. Unsupported agenda and nested-song field names are listed in the migration preview and counted in its unmapped-field total. Service-plan templates created in Smart-Church are local templates and do not claim a ChurchTools source ID.

The resource-booking schema was reviewed from the instance's public OpenAPI document on 2026-10-31; no record endpoint or login token was used. Booking reads require permission to view each resource and may return anonymized details; included person references may be null. The importer must preserve that visibility boundary, link people only by stable source IDs, distinguish recurring-series records from date-range occurrences, and preserve appointment-linked bookings without creating a second unrelated reservation. Booking-history date scope requires owner confirmation. Until the mapping and date-scope decision are implemented and verified, bookings remain a known migration gap.

## Review and conflict rules

- Preview lists total/create/update/review/invalid counts and a sample of up to 40 source records. Unmapped person field names are counted; profile values are stored in the encrypted migration snapshot and then in the private ChurchTools profile. Credential-like keys are excluded recursively. The persons endpoint may return only permission-scoped fields, so this does not prove every configured ChurchTools field was returned.
- Matching uses stable source IDs. Email, group name, and event title/date/time matches are conflicts for review and are skipped during import; records are not merged on those values.
- Existing records linked by a stable ID can be updated. New migration records remain editable and are kept outside scheduled-sync cleanup.
- Group imports add source memberships only; they do not remove existing memberships.
- Source lists must finish within 100 pages of 200 records per endpoint. An incomplete list prevents a preview from being saved. The selected date range applies to events.

## Progress and recovery

The preview snapshot is encrypted using the server's configured encryption key. Import processes at most 50 records in a database transaction and stores its page and created/updated/skipped/failed counts. A record-level database error rolls back only that record, advances the batch, and records its area and stable source ID in the administrator-visible failure summary. Retry migration replays the same snapshot idempotently after the cause is corrected. A batch-level failure rolls back the whole transaction and does not advance the saved page. Keep the server encryption key available until the migration is complete.

Preview and import require location-management permission. Use a dedicated ChurchTools login token with only the required read access. Do not put tokens in issue comments or logs. A complete production migration should first be verified against a non-production ChurchTools site and reconciled against source counts.

## Source API

ChurchTools documents that the installed instance serves its own OpenAPI specification at `/system/runtime/swagger/openapi.json`; endpoint availability and fields can vary by installed version. Review that specification before relying on any mapping or endpoint: [ChurchTools API documentation](https://churchtools.academy/en/help/system-settings/api-en/api-documentation/). The current instance schema is at `https://gfcschweiz.church.tools/system/runtime/swagger/openapi.json`. See also the official [resource booking overview](https://churchtools.academy/en/help/churchtools-modules/resources/overview-of-resources/).
