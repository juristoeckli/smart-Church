# Third-party worker protocol

Status: wire contract for supervised WebSocket workers plus a reusable Node.js client in `@smart-church/worker-sdk`. The general third-party module installer and a module-neutral worker host are not implemented yet. Do not treat this document as a claim that arbitrary workers can already be installed.

## Transport and trust

A worker is a child process started and supervised by Smart-Church Core. Core supplies `SMART_CHURCH_CORE_WS_URL` and `SMART_CHURCH_WORKER_TOKEN` in that process environment. The URL points to a loopback-only WebSocket endpoint; the token is generated by Core for the worker process. Workers must keep the token in memory, must not log it, and must not send it to browser clients or other services. Do not expose the internal endpoint through a public reverse proxy.

Workers use a standard RFC 6455 WebSocket connection with UTF-8 JSON text messages. The current Video endpoint is `/internal/workers/video`; it accepts one active child belonging to its supervisor. The general module host will need to provide an endpoint per module before third-party workers can connect. Use `@smart-church/worker-sdk` for Node workers or a maintained WebSocket client library for another runtime rather than implementing WebSocket framing yourself.

Installed modules are trusted executable code. Process separation limits failure propagation, but it is not a security sandbox. Core remains responsible for authenticating users, checking permissions, and deciding which worker operation may run. A worker must still validate operation input and must scope every read and write to the `departmentId` supplied by Core.

## Connection lifecycle

1. Connect to the supplied WebSocket URL.
2. After the socket opens, send a `register` message with the supplied token.
3. Wait for Core's `registered` response before accepting work. Registration must complete within five seconds.
4. Send `worker-ready` after initialization is complete. The current Video worker reports readiness by sending `registered` to Core after it has initialized its own dependencies.
5. Answer each request with exactly one response using the same request ID.
6. Close cleanly on process shutdown. If the socket closes unexpectedly, the worker process should exit; Core's supervisor owns restart policy and reconnects a fresh child with a fresh token.

Core sends WebSocket ping frames every 20 seconds and closes a connection that has not answered a ping within 40 seconds. Standard WebSocket libraries handle ping/pong frames automatically.

## Messages

All messages are JSON objects. Unknown message types should be ignored only when explicitly described as optional; malformed messages or invalid request envelopes should close the connection.

### Register

Worker to Core, once per connection:

```json
{ "type": "register", "token": "<SMART_CHURCH_WORKER_TOKEN>" }
```

Core replies:

```json
{ "type": "registered" }
```

### Request

Core to worker:

```json
{
  "type": "request",
  "id": "<opaque request ID>",
  "operation": "status",
  "data": {},
  "departmentId": "<department UUID>",
  "actor": "<authenticated user ID>"
}
```

`id` is opaque and must be echoed unchanged. `operation` is defined by the module and must be checked against an allowlist. `data` is module input. `departmentId` and `actor` are trusted context added by Core; never take replacement values from `data`. The current Video supervisor allows at most eight in-flight requests and limits incoming text messages to 1 MiB. Callers set operation timeouts (15 seconds by default for Video); a timeout does not prove that a device command failed, so command workers must report uncertain outcomes honestly and must not blindly repeat a non-idempotent command.

### Successful response

Worker to Core:

```json
{ "type": "response", "id": "<same request ID>", "result": { "online": true } }
```

### Failed response

Worker to Core:

```json
{ "type": "response", "id": "<same request ID>", "error": "Device is unavailable." }
```

Return a concise, actionable error message. Do not return stack traces, credentials, tokens, private configuration, or unrelated user data. Core converts worker errors to an operation failure for the caller.

### Readiness notification

Worker to Core after initialization or recovery:

```json
{ "type": "worker-ready" }
```

## Minimal worker loop

The snippet uses Node's standard `WebSocket` client and shows the message flow. Production workers should add schema validation for their operation payloads, graceful shutdown, and structured logging with secrets redacted.

```js
const socket = new WebSocket(process.env.SMART_CHURCH_CORE_WS_URL);
const token = process.env.SMART_CHURCH_WORKER_TOKEN;
const operations = new Map([
  ["status", async ({ departmentId }) => ({ departmentId, online: true })],
]);

socket.addEventListener("open", () => {
  socket.send(JSON.stringify({ type: "register", token }));
});

socket.addEventListener("message", async ({ data }) => {
  const message = JSON.parse(String(data));
  if (message.type === "registered") {
    socket.send(JSON.stringify({ type: "worker-ready" }));
    return;
  }
  if (message.type !== "request") return;

  const operation = operations.get(message.operation);
  try {
    if (!operation) throw new Error("Unsupported operation.");
    const result = await operation({
      ...message.data,
      departmentId: message.departmentId,
      actor: message.actor,
    });
    socket.send(JSON.stringify({ type: "response", id: message.id, result }));
  } catch (error) {
    socket.send(JSON.stringify({
      type: "response",
      id: message.id,
      error: error instanceof Error ? error.message : "Operation failed.",
    }));
  }
});
```

The sample intentionally passes Core's department and actor context as separate trusted arguments. A real worker should not blindly spread `message.data` over those values.

## Manifest and module boundary

Module manifests currently validate `id`, semantic `version`, required/optional dependencies, enablement, and the module-local server entry. Server modules export `registerModuleRoutes(app, context)`. Core scopes public routes, supplies department resolution and mutation validation, and supervises registered workers. See `apps/api/src/modules/module-sdk.ts` and the built-in module manifests for the current server-module shape.

Third-party module compatibility declarations, requested permissions, UI packaging/loading, installation lifecycle, and a module-neutral worker supervisor remain future work. Until those pieces exist, only bundled workers launched by their built-in supervisors can use internal worker transports.
